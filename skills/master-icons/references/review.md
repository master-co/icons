# 審稿與證據

## 先定義變數

A/B 比較一次盡量隔離一個主變數：框角、點徑、內線數、頭身比例或視覺重心。兩側相同 viewBox、CSS 尺寸、顏色、背景、DPR、文字與空間；4× 診斷圖明確標示倍率。比較不同圖庫時保留各自原始描邊並說明母版／顯示尺寸，不能偷偷重繪對手。

修改前先保存必要的 source / dist 或截圖。不要在完成修改後憑記憶畫「before」。若沒有真實 baseline，就只交付現況與理由，明講缺少前後證據。

## 兩種閱讀距離

原生圖：單顆、同家族、不同結構並排、14 / 16 / 18px 文字旁。先看語意、粗細感、空隙、重心與整組節奏。小圖示必須在實際 CSS 尺寸下檢視；聊天介面可能縮放截圖，需按檔案原始比例開啟。

放大圖：看 tangent、接縫、凹角、端點、重疊和自交。放大能解釋缺陷，不能證明小尺寸可讀。避免只交巨大 SVG 或帶漸層、陰影和旋轉的 hero 卡。

## 缺陷分級

| 類型 | 處理 |
| --- | --- |
| 語意錯誤、裁切、非預期斷線、孔洞消失、不可用的輸出 | 修正後才可稱完成 |
| 家族不一致、過密、重心偏、圓角過頭、曲線不順 | 給具體畫面並修整；未解決就標明待審，不偽稱已定案 |
| 可合理分歧的比例／氣質偏好 | 完成可比較候選與理由，供使用者判斷；不虛構通用最佳數值 |

看 bell-off 的斜線是否仍能辨識原母型，settings 的孔是否存活，file-text 是否黑成一塊，star 的角型是否縮小到顯得失衡。這些是對應結構的提問，不是每輪都要求重畫這四顆。

## 自動化能做什麼

附帶 render-review.mjs 會依現有 dist 生成原生明暗／DPR 1、2 圖稿、16px 四倍診斷、文字情境，以及 padded raster 的邊界、墨量與質心。JSON 中的 clip／empty 可當結構缺陷；墨量與質心只作排查線索，不能轉成美感排名或自動置中指令。

腳本不會認出物件、不檢查所有孔洞、不可證明曲線漂亮，也沒有替人類審稿。browser unavailable 時交付 HTML 與明確未驗證狀態；不要把生成成功改寫成視覺通過。

## 一份有用的審查紀錄

記錄概念／變體、觀察情境、可見問題、修改、對照檔、結果與剩餘問題。需要比較時用簡單表格；不要用「8/10 精緻度」之類沒有量測定義的總分。

完成條件是此次要求的圖稿、必要變體、相關驗證和可查看證據俱全。alpha 可維持可用但待設計定案；使用者尚未審稿不等於不能交付，也不授權先擴到未要求的幾百個圖示。

## 精修歷史與審查可追溯性

整庫審查不等於整庫修改。逐項記錄保留的具體理由；修改項目另記缺陷、尺寸、處理及新的目視證據。不要把前一輪的「已看過」當成本輪結論，或只改 hash 來使驗證通過。

使用者肯定一組案例後，先把偏好翻譯成可觀察的判斷，再拿其餘圖示驗證。例如本次縮排的內容位移、擴音器／握手的結構曲線、票券撕線的局部端帽，是三種不同問題；不能簡化成「多加弧線與細節」。保存已肯定版本，以真正的構造缺陷或新要求為修改依據。若使用者要求獨立複審，複審者仍須逐顆檢視，不繼承前輪通過標記；主代理再核對修改與證據。

歷史基準保護的是可追溯性，不是永久禁止使用者授權的精修。保存真實 before 與舊 ledger 後，可將「全部圖稿必須不變」改成：本輪未修改項目精確相同；修改項目有明確清單、前後 hash 和審查結果。來源角色若由比較轉為實際沿用／重繪，也要同步 notices、SVG 單檔下載、ZIP 和 React 套件，普通圖庫仍不需逐顆顯示來源標籤。
